## 0.11.6

macOS で「録音がプツプツ切れて音質が悪い」報告（2026-08-01・65 分の会議録音）の修正です。**macOS の方は `sysrec` バイナリの入れ替えが必要です**（下記「内部」参照）。

### 修正

- **Bluetooth イヤホンなど 44.1kHz 出力のとき、録音が 1 秒に約 4 回プツプツ切れる問題を修正**（macOS）。実害の録音では 65 分のうち **318 秒（8.1%）が無音に置き換わって**いました。切れていない部分も音が **8.8% 詰まって（＝約 1.5 半音高く）**記録されます。
  - 原因は取り込みサンプルレートの取り違えです。出力デバイスが実際には **44100Hz** で動いているのに、取り込みが **48000Hz** とラベルされていました。1 − 44100/48000 = **8.1%** ぶん実時刻に追いつけず、**0.25 秒ごとに 15〜20ms の無音**が挟まります。
  - 0.11.1 で入れた対策（集約デバイスの公称レートを聞いてラベルを貼り替える）は**通常は効きます**が、公称レートがまだ実レートを反映していない瞬間があり、そのときは 48000Hz のまま録音の最後まで走り続けていました（0.11.5 まで）。
  - 対策として、**届いたフレーム数 ÷ 実時刻で入力レートを実測し、ラベルが違っていれば実測値へ差し替える**仕組みを入れました。デバイスの申告に頼らないので、原因が何であれ**録音開始から約 3 秒で自動的に正常へ戻ります**（その 3 秒ぶんだけ影響が残ります）。システム音・マイクの両方に効きます。
  - 実測（BT 出力 44.1kHz・疑似再現）: 取りこぼし **8.1% → 0.9%**（＝補正が効くまでのぶんのみ）。正常な環境では補正は作動しません。
- **停止時の診断が、サンプルレート不一致を「CPU 負荷が高い可能性があります」と誤って説明していた問題を修正**。判定を出力側のレートと比べていたため、レート違いを取り違えていました。実測レートとラベルを直接比べるようにし、**「実測入力 44121Hz / ラベル 48000Hz — デバイスのサンプルレート不一致です」**と原因を名指しします。

### 既知の制約

- 誤検知を避けるため、実測での補正は **①取りこぼしのあった測定窓は使わない ②実測値が標準レート（44100 / 48000 / 16000 など）の 1% 以内に乗ったときだけ ③同じ結論が 2 窓続いたときだけ** 採用します。このため補正が効くまでに約 3 秒かかります。
- 録音中に Bluetooth イヤホンが通話モード（HFP・16kHz）へ切り替わると、システム音の帯域は 16kHz 相当まで落ちます（OS 側の仕様です）。レート追従自体は従来どおり行われます。

### 内部

- ⚠️ **`sysrec` バイナリを更新しました。macOS の方は診断（doctor）の「sysrec を取得」で入れ替えてください。** CLI 契約は変わっていない（abi 2 のまま）ため自動では促されませんが、**入れ替えないと今回の修正は効きません**。
- 自己補正は `CaptureLane`（`native/sysrec/sysrec.swift`）に実装。`LaneStats` に実測入力レートとラベルレートを追加し、停止時の診断がそれを使います。
- 手動 E2E に **ROB-03g**（デバイスの公称レートが誤っていても実測で自力復帰すること・および正常環境で誤検知しないこと）を追加。ROB-03e に、AAC 圧縮で無音が埋もれて `silencedetect` に出ない場合の検出方法（5ms 包絡の変調スペクトルに 3.9〜4.1Hz とその倍音が立つ）を追記。
